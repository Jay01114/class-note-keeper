# 架构与数据流详解

## 总体链路

```
手机（自带录音机）
   │  录课完成（m4a/mp3 等）
   ▼
LocalSend（局域网直传，唯一手动动作）
   │
   ▼
PC: inbox/ 文件夹（收件箱）
   │  轮询检测（3 秒/次）
   │  文件大小连续 6 秒不变 = 传输完成 → 入队
   ▼
faster-whisper（本地转写，medium/large-v3，int8）
   │  输出：全文 + 时间戳
   ▼
Qwen2.5 via Ollama（本地 LLM）
   ├─ 第一次调用：识别 学科 / 课程名 / 标题（从固定学科列表选）
   └─ 第二次调用：生成详细知识点罗列纪要
   ▼
归档到 Obsidian vault/
   ├─ 学科/原材料/{日期}_{标题}.m4a + .meta.json
   ├─ 学科/纪要/{日期}_{标题}.md
   └─ 学科/转写/{日期}_{标题}.md
```

## 模块职责

| 模块 | 文件 | 职责 |
|---|---|---|
| 配置加载 | `core.py` | `config.json` 查找（环境变量 `KETANG_CONFIG` → 当前目录 → 脚本目录） |
| 文件监视 | `core.py` / `app.py` Worker | 轮询 inbox；`is_ready_audio()` 做完整性检测（忽略 `.part/.tmp/.crdownload`，大小稳定 6 秒） |
| 去重 | `core.py` | 归档时记录文件 SHA-256；启动时扫描 vault 构建已处理集合，重复内容自动移入 `_重复/` |
| 转写 | `core.py` | faster-whisper（ctranslate2），`int8` 量化，语言自动检测 |
| 学科识别 | `core.py` `_classify()` | 短 prompt 只输出三行（SUBJECT/COURSE/TITLE），`normalize_subject()` 做简称模糊匹配 |
| 纪要生成 | `core.py` `_summarize()` | 单独一次调用，输出 SUMMARY_START/END 之间的知识点罗列正文 |
| 归档 | `core.py` `archive()` | 音频/纪要/转写分开落盘，学科归一化（未知 → 待整理） |
| 桌面 UI | `app.py` | PySide6：任务表格、转写进度条（按时长估算）、日志、托盘、单实例锁 |
| Ollama 生命周期 | `app.py` | 管家启动时拉起 serve（SW_HIDE 防终端弹窗），退出时收起（只收管家拉起的） |

## 关键设计决策

### 1. 为什么要"两步调用"而不是一次生成
早期版本让 LLM 一次输出学科+标题+纪要，Qwen2.5-7B 面对长转写文本经常不遵守格式（输出自由回答），导致解析失败。拆成两次调用后：
- 第一次 prompt 极短（只看转写开头 12000 字符），只输出三行元数据 → 格式遵从率高；
- 第二次只输出正文（两个分隔符之间）→ 模型专注内容。

### 2. 为什么串行不并行
转写（~2GB 显存）+ 纪要（~4.7GB 显存）都吃 GPU。8GB 显存下并行会 OOM 且互相拖慢。串行批量处理对"晚间整理"场景足够快。

### 3. 为什么"文件大小稳定 6 秒"才处理
LocalSend 传输中的文件会被轮询扫到，直接转写必然失败。用"大小连续 6 秒不变"判断传输完成，简单可靠。

### 4. 为什么学科用固定列表
课堂笔记的学科是有限集合。固定列表避免 LLM 自创"数学/英语/物理…"等散乱目录；未知内容进 `待整理/` 而不是新建学科。

### 5. 为什么不常驻后台
本方案定位"晚间批量整理"：打开应用才监视，关闭即全停。省内存、无开机自启、隐私更好。

## 数据落盘格式

```
vault/
└── 概率论/
    ├── 原材料/2026-08-31_条件概率与公理化概率空间.m4a
    ├── 原材料/2026-08-31_条件概率与公理化概率空间.meta.json
    ├── 纪要/2026-08-31_条件概率与公理化概率空间.md
    └── 转写/2026-08-31_条件概率与公理化概率空间.md
```

- 文件名 = `日期_课程标题`，按名称排序即时间线
- `纪要.md` 带 frontmatter（title/subject/course/date/tags），可被 Obsidian 检索与图谱
- `meta.json` 记录 file_hash，供去重
